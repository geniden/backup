1. Overview & architecture

Layered backup protection

What most backup tools skip — you choose how far to go.

The usual problem: one computer collects and stores all backups. If that machine is stolen, copied, or compromised, everything is exposed — archives, database dumps, and often passwords stored in the same place. This system is built so you can stack independent protections; each level is optional except the baseline transport encryption.

  1. TLS transport (baseline) Private CA, certificate pinning — WSS + HTTPS. Mandatory for every connection; no plaintext backup channel in production.
  2. Server-side encryption (Encrypt mode) Per-task Encrypt mode on in backup-client. The server encrypts each backup with AES-256-GCM before download; your storage receives *.aes files, not readable ZIP/TXT. Key stays in server encrypt_password only.
  3. Hardware-bound client (device_id) Hybrid binding to your backup PC — fingerprint computed at runtime, not stored on disk. The server accepts only that machine; copying the client install to another PC does not grant access.
  4. Secrets on the server (Production mode) Connection menu → Secrets mode: Production. After sync, DB passwords and similar fields live only in server backup.db; the client keeps task names and schedules without db_pass.
  5. Decrypt tool on external media backup-decrypt + decrypt.toml on a USB stick — decryption password separate from the backup PC. Optional output_path writes plaintext to another drive (e.g. flash) without leaving decrypted files on the main disk.

In practice three or four layers cover most threats; all five address the “single unprotected backup PC” scenario. See Security model for details and Decrypting .aes backups for level 5.

The Backup System is a distributed backup solution for your own VPS servers (Windows and Linux). A central backup-client schedules tasks, connects to remote agents over an encrypted channel, and stores downloaded archives locally. Each VPS runs a lightweight backup-server agent that executes dumps, file archives, or shell scripts on demand.

Supported task types

  • mysql_dump / mariadb_dump — MySQL/MariaDB dump, ZIP archive
  • postgresql_dump — PostgreSQL dump via pg_dump, ZIP archive
  • sqlite_dump — SQLite file copy
  • files_archive — ZIP archive of a directory (with ignore patterns)
  • dir_sync — incremental ZIP of new files only (by mtime on server); one archive per run
  • shell — Run an authorized script from data/scripts/, output saved as text (backup_{slug}_shell_{YYYY-MM-DD}_{HHMMSS}.txt)

dir_sync (incremental media sync)

Use with a database dump task for sites that store uploads on disk (e.g. product images, PDFs, archives). The server keeps a cursor (sync_last, sync_last_path) in backup.db and ships files in batches (oldest by modification time first). Parameter Max batch MB (default 200) limits uncompressed data per ZIP; values above 500 are capped. Smaller batches are recommended on small VPS. Schedule frequently (e.g. every 15 minutes) until the initial backfill finishes (no_changes), then switch to weekly for new uploads only. If a file recorded in sync_last_path was deleted on the server, the next run continues from the cursor without error. All file types are included (any extension) — not only images. First sync window: 0 = all files in the folder; N = only files from the last N days on the first run only. If nothing is pending after the cursor, the run completes with no_changes (no download). Archives are stored as ZIP on the client (no auto-unzip). Encryption is not available for dir_sync. Uses the built-in Rust ZIP writer — the system zip package is not required for dir_sync.

Reset synchronization (start fresh)

In the task menu for a dir_sync task, the line Last received file: … shows the name of the most recent archive (from run history or from files on disk), for example backup_orlovka_sync_2026-07-04_105014.zip. Select it to confirm Reset synchronization (start fresh)?

  • Server — the incremental cursor in backup.db (task_sync_state) and any pending batches are cleared. The next run behaves like a new backfill (respecting First sync window).
  • Client — run history for that task in backup.db is cleared (task_runs, last_run).
  • Local ZIP files are not deleted — existing backup_*_sync_* archives stay in data/backups/<slug>/. After reset, new runs create new archives with new timestamps in the filename; you may have overlapping content if you kept old ZIPs.

Use this when you accidentally deleted one or more backup_*_sync_* archives locally and need the server to ship those files again, or when you want to re-run the initial backfill without recreating the task. Requires a live connection to the VPS (the client sends reset_dir_sync over WSS).

files_archive (full project / tree snapshot)

One ZIP of the entire tree each run (with ignore patterns for node_modules, etc.). There is no batch limit — typical app trees (~100–300 MB with ignores) fit a single monthly run. Use dir_sync instead when uploads or media grow to many gigabytes and need incremental batches.

Encrypt mode (per task)

In the task menu: Encrypt mode (on/off). When on, the server encrypts the backup with AES-256-GCM before download (name.zip.aes or name.txt.aes). The server must have encrypt_password in config.toml (same value in backup-decrypt on USB). If Encrypt mode is on but the key is missing, the server skips the run and logs a warning. New tasks default to Encrypt mode off. dir_sync does not support encryption.

Backup retention (local disk)

Per connection: menu → Retention. Options: Never (0), 7, 14, 30, or 60 days. Old backup files under data/backups/<slug>/ are removed automatically when:

  • the connection is enabled;
  • a backup task completed successfully (trigger);
  • at most once per 24 hours per connection (cooldown);
  • the latest backup per task is always kept, even if older than the retention period;
  • dir_sync archives are never deleted — incremental batches form a required history; retention applies only to other task types.

Disabled connections never run retention — local files are not touched.

Typical data flow

  1. Scheduler fires a task by cron expression.
  2. Client opens a WebSocket session to the server if needed (see below), syncs task definitions, and sends run_task with def_id over WSS.
  3. Server queues the job, executes it, and responds with task_completed plus an HTTPS download URL.
  4. Client downloads the file, verifies SHA256, records the run in backup.db.
  5. Client sends check_download; server deletes the temporary file.
  6. When no further tasks are due within 10 minutes, the client closes the WebSocket (session sleeps until the next cron tick).

WebSocket sessions (scheduler)

The scheduler does not keep a permanent WebSocket open all day. Each enabled connection (each VPS) uses a short backup session:

  • Wake — shortly before a cron run, the client connects (TLS + device_id auth + sync_tasks).
  • Work — tasks run in order; downloads and check_download use the same session.
  • Stay open — if another task on the same server is scheduled within the next 10 minutes, the link stays up (e.g. staggered 0, 5, 10, 15 … minute crons in one evening window).
  • Sleep — when all pending work is finished and the next cron is more than 10 minutes away, the client closes WSS. No heartbeat traffic while idle.

Many connections (many VPS) are independent: each has its own schedule, session, and server queue. One physical server address (IP:port) still shares a single WSS link on the client (deduplicated by URL).

If the link drops while a task is still in progress, the client runs a separate recovery loop (reconnect every few seconds, wait for completion, re-submit if needed). That is different from the three submission retries used when the queue cannot be reached at cron time. If the server reports a real task error (missing folder, dump failed), the task is logged as failed and skipped — recovery is not used.

2. Security model

The system is designed for operators who manage their own infrastructure. It follows established practices for private PKI, encrypted transport, and least exposure of secrets on remote servers.

What the application provides

  • Private TLS (WSS + HTTPS) — No public CA or domain name required. Each server gets a certificate signed by your client-side root CA (~10 years validity). Server certificates are issued for ~730 days and can be renewed from the client menu.
  • Certificate pinning — The client stores the server certificate fingerprint and accepts only that certificate for the connection.
  • Device ID authentication — The client computes a hardware fingerprint (device_id) at runtime and sends it over TLS. The server registers it on first connect and rejects other machines. Nothing is stored on the client disk for this.
  • Test vs Production secrets mode — Per connection, you choose where database passwords live:
    • Test — full task parameters (including db_pass) stay in client backup.db at all times. Use while setting up tasks.
    • Production — after each successful sync_tasks, the server stores full tasks in backup.db on the VPS; the client removes db_pass from mysql_dump / postgresql_dump tasks locally. Scheduled runs use only def_id; the server runs dumps with passwords from its database.
    Toggle in the connection menu: Secrets mode: Test / Production. To change a password in Production: edit the task on the client, enter the new password, reconnect (sync updates the server). An empty password on the client never overwrites the server copy.
  • Download integrity — Every completed backup is verified with SHA256 before being marked successful.
  • Shell script sandboxing — Scripts run only from data/scripts/; path traversal in script names is rejected.
  • Single active client per server — Only one WebSocket session per backup-server agent at a time. A new connect from the same client replaces the previous session (reconnect / recovery). On the client, you can register only one connection per unique server address (IP:port); a duplicate address is blocked when adding or editing a connection.
  • Temp file cleanup — Archives are removed from the server after the client confirms download.

Administrator responsibilities

Root CA on the client (data/ca/root.crt and data/ca/root.key)

The private root CA is the trust anchor for all your backup servers. The application creates and uses it automatically, but protecting the root key is entirely your responsibility as the system administrator. Store the client installation on a machine you control, restrict filesystem access, and include root.key in your backup and disaster-recovery procedures. If the root key is compromised, recreate the root CA from the client menu and renew every server certificate.

Server config.toml and TLS private key

Each server agent stores device_id in config.toml (empty until your client connects). Protect the file with standard server hardening — same as for TLS keys and service credentials.

Recommended layout on Linux:

  • Install under /opt/backup-server/ (or similar dedicated path), owned by a non-web user such as root or a dedicated backup account.
  • Set restrictive permissions: chmod 600 tls/server.key config.toml.
  • Do not place the agent under /var/www or any path served by your web stack — the backup port is for your client only, not for public website traffic.
  • Use a firewall so only your backup client’s IP (or VPN) can reach the server port (default 8080).

With TLS, pinned certificates, firewall rules, and proper file permissions, the server agent is suitable for production use on private VPS instances.

Client machine

  • In Test mode, protect backup.db — it contains database passwords.
  • In Production mode, dump passwords are removed from the client after sync; protect server backup.db on the VPS instead.
  • Protect data/ca/root.key — see above.
  • Run the scheduler on a stable host (office server, management VM, or your PC with UPS).

3. Client & server deployment

Step 1 — Install the client

Copy to one folder (examples):

Windows:  C:\backup-client\backup-client.exe  (+ backup-monitor.exe optional)
Linux:    /opt/backup-client/backup-client      (+ backup-monitor optional)

First launch creates backup.db and, if needed, the root CA under data/ca/.

UI language: main menu → Settings → Language. Built-in locales: English, Russian, German, French, Chinese (Simplified, zh-CN). Server console messages follow BACKUP_LANG or LANG (same set).

Step 2 — Add a connection

  1. Run backup-client (interactive menu).
  2. Choose Add connection.
  3. Enter a latin slug (e.g. production) and server address IP:port (default port 8080).
  4. The client generates a server certificate signed by your root CA and prepares a deploy folder: data/ca/{slug}/

Deploy folder contents

The client writes data/ca/{slug}/ on your PC. Copy the contents of that folder to the VPS (not the slug folder itself). The Linux backup-server binary is not inside the bundle — build or copy it separately.

Step 3 — Deploy to the VPS

# Copy bundle files + backup-server binary into one directory, e.g. /opt/backup-server/
scp data/ca/production/config.toml data/ca/production/service.sh user@vps:/opt/backup-server/
scp -r data/ca/production/tls user@vps:/opt/backup-server/
scp backup-server-linux user@vps:/opt/backup-server/backup-server

ssh user@vps
cd /opt/backup-server
chmod +x backup-server service.sh
chmod 600 tls/server.key

# Optional: test interactively (needs config + tls; shows first-run hints if files missing)
./backup-server

# Install and start as service (sets ownership, verifies "Listening on https://" in journal)
sudo ./service.sh

service.sh requires config.toml and tls/, runs chown on the install directory for the service user (SUDO_USER when you use sudo), enables systemd, and fails with logs if the server does not start within ~20 seconds.

Step 4 — Add tasks, choose secrets mode, start scheduler

  1. In the client menu: open the connection → Add task.
  2. Configure task type, parameters, and cron schedule.
  3. While testing, keep Secrets mode: Test (default).
  4. When ready for production: connection menu → Secrets mode: Production, then Test connection once to sync and clear local DB passwords.
  5. From the main menu: Start scheduler (or run backup-client serve).

See also Backup retention in the overview.

Changing a password in Production: edit the task on the client, enter the new password, reconnect. Sync sends the new value to the server. If the client password field is empty, sync does not overwrite the server password.

One connection = one server = one certificate

Each connection has its own TLS certificate and device_id binding on the server. If you manage 15 VPS servers, you create 15 connections — each with a unique slug and certificate.

One server address per connection (by design)

The client allows only one connection per unique IP:port. Adding a second connection to the same server address is rejected. This avoids duplicate certificates, conflicting slugs, and ambiguous deploy folders.

On each VPS, backup-server accepts only one active WebSocket client at a time. The scheduler opens a session when tasks need to run and closes it after idle (see WebSocket sessions). A manual Test connection while the scheduler is connected to the same server may briefly replace that session; avoid overlapping tests during backup windows.

Certificate renewal (~2 years)

Server certificates are valid for about 730 days. Before expiry:

  1. Client menu → connection → Renew server certificate.
  2. Copy the updated data/ca/{slug}/ folder to the VPS (new cert; device_id reset in bundle).
  3. Restart backup-server: sudo systemctl restart backup-server.
  4. The client updates the stored fingerprint automatically; device_id re-registers on first connect.
Recreate root CA (main menu) invalidates all server certificates. After recreating the root CA you must renew the certificate for every connection.

4. Client hardware requirements

This section applies to the machine that runs backup-client (interactive menu or backup-client serve) and stores downloaded backups under data/backups/ or your custom folder. Heavy work (database dumps, ZIP creation, shell scripts) runs on each VPS; the client opens WebSocket sessions on demand and downloads finished archives over HTTPS.

Recommended configurations

ProfileCPURAMStorageTypical use
Minimum 2 cores / 4 threads 8 GB SSD, free space ≥ 2× your largest expected backup set Up to ~10 VPS, small DB dumps and archives (tens of MB), schedules staggered across connections
Comfortable (recommended) 2–4 cores 16 GB SSD (dedicated partition or disk for backups) Up to ~30 VPS, mixed task types, occasional overlapping downloads
High load / many large archives 4+ cores 32 GB or more Fast SSD or NAS with stable write speed Many VPS, large ZIPs, or several big downloads finishing at the same time

What actually uses CPU and RAM on the client

  • Idle scheduler — between cron windows the client keeps no WebSocket open (sessions sleep). CPU and network use while waiting for the next task are negligible, even with many VPS connections registered.
  • Peak load — downloading backups over HTTPS, verifying SHA256, and writing files to disk. TLS and hashing are moderate; RAM and disk throughput matter more than raw CPU during bursts.
  • Per server — the agent runs at most one backup job at a time for that VPS. Different servers can finish jobs around the same time, so the client may download from several connections in parallel.

RAM planning (downloads)

Each completed backup is downloaded into memory before it is written to disk (then verified with SHA256). Rough peak memory: 

RAM_peak ≈ OS + backup-client + (parallel_downloads × largest_file_size) + safety margin

Example (comfortable): 5 connections finish at once with archives of ~400 MB each → ~2 GB for download buffers, plus ~2–4 GB for the operating system and GUI → about 8–10 GB peak. 16 GB RAM is usually comfortable for this pattern.

Critical worst case

If all 30 VPS finish at the same moment with archives of 1 GB each, the client could need on the order of ~30 GB just for download buffers (before OS overhead). That scenario is unlikely if cron schedules are spread out, but it explains why you should not align every task on every connection to the same minute.

Stagger schedules — between servers and within one VPS

You do not need (and should not try) to run all backups at exactly the same time.

Many connections (many VPS)

Spread cron times across connections — for example:

  • Server A: 0 8 * * * (08:00)
  • Server B: 15 8 * * * (08:15)
  • Server C: 30 8 * * * (08:30)

This keeps client RAM, disk writes, and your uplink predictable.

Many tasks on one connection (one VPS)

On a single server, tasks run one at a time on the agent (queued on the server). They are not lost when queued, but if every task uses the same minute you get a long serial backlog, higher VPS load, and longer waits before the last site finishes.

Recommended: offset the minute field by 5–15 minutes per task, same hour:

# Avoid — all at once (works, but heavy):
0 22 * * *   site-a dir_sync
0 22 * * *   site-b dir_sync
0 22 * * *   site-c mysql_dump

# Better — stagger minutes:
0 22 * * *   site-a dir_sync
5 22 * * *   site-b dir_sync
10 22 * * *  site-c dir_sync
15 22 * * *  site-d dir_sync
20 22 * * *  site-e mysql_dump

For initial bulk sync you may use shorter intervals (e.g. */5) temporarily; switch to staggered nightly times once caught up. At each cron tick the client opens a session if needed, waits for task_queued, and retries submission up to 3 times (60 s apart) if the server cannot be reached; after that it logs SKIPPED this run until the next cron tick. If the link drops after the task was queued, recovery reconnects and may re-submit automatically (see WebSocket sessions).

Storage (SSD) and operating system

  • SSD strongly recommended for the backup root — faster writes during download bursts and smoother retention cleanup.
  • Keep at least 15–20% free space on the backup volume; retention deletes old files but does not replace off-site copies.
  • Windows 10/11 and Ubuntu LTS (desktop or Server) are both supported. For a dedicated backup PC:
    • Ubuntu Server (no GUI) — slightly lower RAM use and smaller attack surface.
    • Windows with GUI — fine if you already use it; budget an extra ~2–4 GB RAM for the desktop.
  • Security depends more on patching, firewall, and who can access the backup folder than on the choice between Windows and Linux.

See also Security model (client machine) and Limitations (server-side archive RAM limits).

6. FAQ & troubleshooting

Scheduler / connection

Monitor shows dashes (—) for a task

No successful run is recorded yet. Ensure backup-client serve is running, the connection is enabled, and the task has completed at least once with a successful download.

Task queue on one connection

When several tasks fire close together, the server accepts each run_task into a FIFO queue and runs one job at a time. You may see position N in server queue in client logs — that is normal. Spread cron minutes (see hardware / scheduling) to shorten the queue and reduce peak load.

Connection busy (legacy servers)

Current servers always queue run_task requests (one active run per connection). The client waits for task_queued and retries submission up to 3 times (60s apart) before skipping a cron tick and logging an error.

WebSocket session sleeps between tasks

Normal behaviour: after backups finish, if the next cron for that server is more than 10 minutes away, the log may show the session closing and Scheduler idle — WebSocket opens before the next scheduled task on startup. Before each run the client connects again (auth + sync). Tasks within 10 minutes share one session.

Link lost during a backup

If WSS drops while a task is still pending (dump running or download not finished), the client starts recovery: reconnect (every few seconds), wait up to ~90 s for the server to finish, then re-submit the task if needed. Success is logged as Pending backup task(s) completed after reconnect. If recovery exhausts its attempts, the log reports that the task was not completed in that cron window.

Task failed on the server (broken task)

Missing source path, dump error, or script failure: the server sends task_failed. The client logs that the task is broken and skipped (with the server error) and moves on. Recovery is not used — fix the task configuration or server paths and wait for the next cron.

No active WebSocket connection (legacy)

Older clients required a permanent connection before cron could run. Current scheduler opens WSS automatically before each task. If you still see this message, update the client binary. Otherwise check: scheduler not running, server down, firewall, or TLS/fingerprint mismatch — test with backup-client connection-test <slug>.

TLS / certificate errors

  • Certificate expired — renew from the client menu and redeploy to the VPS.
  • Wrong fingerprint — connection points to a different server or cert was replaced manually.
  • Root CA recreated — renew every server certificate.

Server-side

mysqldump / pg_dump not found

Install the database client tools or set paths in config.toml (mysqldump_path, pg_dump_path).

On Windows, set the full path in config.toml, e.g. mysqldump_path = "D:/mysql/bin/mysqldump.exe" (backslashes in double quotes are auto-normalized on load).

Running backup-server on Windows

Place config.toml and tls/ next to backup-server.exe (or run from the server directory with cargo run). TLS is mandatory. Shell tasks should use .bat / .cmd scripts, not .sh.

Enable verbose server logging (debug mode)

Edit config.toml on the server:

debug = true

Restart the service. With debug = true you get detailed debug logs and memory usage reporting when the process exceeds ~100 MB.

Return to normal operation: debug = false and restart.

How do I remove database passwords from the client?

Open the connection → Secrets mode: Production, confirm, then run Test connection (or start the scheduler). After a successful sync, db_pass is cleared locally for MySQL/MariaDB/PostgreSQL dump tasks. Full tasks remain on the server in backup.db.

How do I change a DB password in Production mode?

Edit the task on the client, enter the new password, save, then reconnect. The next sync sends the new password to the server. Leaving the password empty on the client does not overwrite the server copy.

Client

data/backups/{connection-slug}/

Yes — one backup.db per client installation manages all connections and tasks.

No. backup-client serve and data/backup.log are sufficient for production.

Cron schedule format

Standard 5-field cron (minute hour day month weekday). Examples:

  • 0 */6 * * * — every 6 hours
  • 0 2 * * * — daily at 02:00
  • */5 * * * * — every 5 minutes (testing)
  • */60 * * * * or 0 * * * * — every hour (shorthand */60 is accepted)
  • */120 * * * * or 0 */2 * * * — every 2 hours

mysqldump_path Path to mysqldump binary. mysqldump on PATH, or full path (e.g. D:/mysql/bin/mysqldump.exe on Windows)
pg_dump_path Path to pg_dump binary. pg_dump (from PATH)
tls_cert Server TLS certificate (PEM). tls/server.crt
tls_key Server TLS private key (PEM). tls/server.key — protect with chmod 600.

8. Decrypting .aes backups (backup-decrypt)

Build decrypt/ (crate backup-decrypt) and keep the binary + decrypt.toml on a USB stick (defense layer 5). Encryption passwords live on the server and on USB — not in client backup.db.

When you need connection names

Each VPS connection in backup-client has a slug (latin name, e.g. production, staging). Downloaded files go to data/backups/<slug>/. That slug is the connection name in backup-decrypt.

Add one entry per VPS in the app (List connections → Add connection) or in [profiles] in decrypt.toml. Connection name = subfolder under your backups root (same slug as in backup-client): 

path = "E:/backups"
output_path = ""          # empty = next to .aes; or e.g. F:/decrypted

[profiles]
production = "encrypt_password from production VPS config.toml"
staging = "encrypt_password from staging VPS"

Layout on disk (same as backup-client downloads): {path}/{connection-name}/backup_….zip.aes. When you browse to …/production/file.zip.aes, the tool picks the production password automatically.

Password format

Any length and text — passphrase, words, or a generated string. Must match encrypt_password on that server exactly. The menu can generate a random 28-character password; copy the same value to the server, enable Encrypt mode on tasks, and restart backup-server.

Main menu

  • Browse .aes files — folder browser under the configured root
  • List connections — add a connection (name + auto-generated password) or edit existing ones
  • Settings — backups root folder and optional output path for decrypted files
  • Exit

Per connection: change name, change password (visible input), regenerate random password, or delete.

output_path

Empty (default): backup_foo.zip.aes → backup_foo.zip beside the encrypted file. When set: writes to {output_path}/backup_foo.zip (folder created if needed). If the path is unavailable (USB unplugged), the tool errors — no silent fallback.

CLI

backup-decrypt                              # interactive menu
backup-decrypt --key-file E:\decrypt.toml
backup-decrypt E:\backups\production              # browser starting in subfolder
backup-decrypt --file path\to\file.zip.aes
backup-decrypt --file file.zip.aes --profile production

--profile selects a connection name from [profiles] when auto-detection from the path is not enough.

Do not commit decrypt.toml

It contains encryption secrets. Add it to .gitignore on any machine where you edit it.

9. Limitations & archive behaviour

File archives (files_archive, dir_sync)

  • All extensions — every regular file under the source directory is a candidate (images, PDFs, ZIP, etc.). dir_sync does not filter by type.
  • No extra copy in temp — the server builds one ZIP directly in data/temp; source files are read in place, not copied as loose files first.
  • UTF-8 names — Cyrillic and Latin filenames are supported. Files whose names are not valid UTF-8 on the server filesystem are skipped (logged on the server).
  • Broken / unreadable files — if a file cannot be read or added to the ZIP (permissions, I/O error, invalid entry name), it is skipped; the rest of the archive continues.
  • 50 MB per file (RAM) — each file is loaded entirely into memory before being written to the ZIP. Files larger than 50 MB are skipped automatically. Very large archives made of many small files can still be large in total (your test: ~106 MB ZIP is fine).
  • Instability risk — on a VPS with little RAM, many concurrent large files or other services may cause slow archives or OOM kills. Prefer weekly dir_sync for uploads instead of archiving the whole tree with files_archive every day.
  • ZIP archives — all task types (files_archive, dir_sync, DB dumps) use the built-in Rust zip crate. No system zip package required on Linux or Windows.

Implemented features (v1.0)

FeatureSummary
Retention Per-connection local cleanup: 0 / 7 / 14 / 30 / 60 days; latest backup per task kept; dir_sync archives never deleted.
dir_sync Incremental directory sync; max_batch_mb; cursor reset from task menu; no encryption.
Per-task Encrypt mode Client task menu; server encrypts when encrypt_password is set.
backup-decrypt Multi-connection passwords in decrypt.toml; browser; optional output_path to USB.

Log sizes are shown in human-readable form (KB / MB), e.g. completed backup_catalog_sync_….zip (106.2 MB).
