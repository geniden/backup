# Backup System — настройка за один вечер

> **⏱️ Быстрый старт:** 15 минут до первого бэкапа  
> **🎯 Цель:** Отдельная коробка (неттоп) → бэкапы с VPS → шифрование на флешке  
> **💻 Для кого:** Есть VPS, хочешь бэкапы по расписанию без облаков и подписок  
> **📸 Скриншоты:** Вставляй в `docs/screenshots/`, замени `[📷 ...]` на свои файлы

---

Обслуживаю сайты и сервера небольших компаний — в основном это SaaS сервисы и интернет-магазины. Для моей работы нужно резервное копирование баз данных и файлов сайтов моих клиентов. Конечно, лучший вариант — это слепок с диска, но это очень большой объём, и мне достаточно дампа БД + новые файлы после расширения каталога интернет-магазина. Не параноик, но безопасность данных в моих руках.

Могу установить backup-client (оркестратор) на VPS, но для меня надёжнее иметь бэкапы под рукой, а не где-то в интернете.

**Почему так:**
- ✅ Бэкапы на отдельном неттопе (украли/сломался рабочий ноутбук — бэкапы не потерялись)
- ✅ Отдельный `device_id` для backup-PC (безопаснее)
- ✅ Неттоп тихий, 35W, крутится 24/7
- ✅ Пароли от БД на сервере (в production режиме), не на клиенте
- ✅ AES шифрование, ключи на флешке

Многоуровневая защита резервного копирования — то, что большинство инструментов резервного копирования пропускают.

Один компьютер собирает и хранит все резервные копии. Если эту машину украдут, скопируют backup-client и скомпрометируют данные, всё окажется уязвимым — архивы, дампы баз данных и часто хранящиеся пароли в том же месте.

Backup system имеет 5 уровней защиты:

1. **Транспорт TLS (базовая линия)**  
   Частный CA, закрепление сертификата — WSS + HTTPS. Обязательно для каждого соединения.

2. **Серверное шифрование (режим шифрования)**  
   Включите режим шифрования для задачи. Сервер получает инструкцию шифровать каждую резервную копию с помощью AES-256-GCM перед загрузкой; ваше хранилище получает файлы, а не читаемые ZIP/TXT. Ключ `encrypt_password` хранится только на сервере.

3. **Аппаратно-ориентированный клиент (device_id)**  
   Гибридное привязывание к вашему резервному ПК — fingerprint вычисляется во время выполнения. Передается на сервер при первом соединении, и далее сервер принимает только эту машину.

4. **Секреты на сервере (Production режим)**  
   Меню подключения → режим Secrets: Production. Пароли баз данных и подобные уязвимые поля удаляются с backup-client, их копии хранятся только в backup-server для создания дампов/бэкапов.

5. **Инструмент расшифровки на внешних носителях**  
   Утилита backup-decrypt на USB-flashdrive — это менеджер профилей соединений, позволяет генерировать уникальные пароли шифрования, расшифровывать "zip.aes" через выбранный профиль.

### 1.3. Копирую файлы на VPS

Используй **WinSCP** (режим Binary), **FAR Manager** (SFTP плагин) или **scp** из PowerShell.

**На VPS создаю папку:**

```bash
mkdir -p /opt/backup
```

**Копирую с ПК (PowerShell, OpenSSH):**

```powershell
# 1. Содержимое папки bash02 (config, tls, service.sh)
scp -r C:\backup\client\data\ca\bash02\* user@203.0.113.10:/opt/backup/

# 2. Сам бинарник server (распакуй tar.gz в C:\backup\server\ заранее)
scp C:\backup\server\backup-server user@203.0.113.10:/opt/backup/
```

**Или используй WinSCP:**
- Режим передачи: **Binary**
- Копирую всю папку `C:\backup\client\data\ca\bash02\` → `/opt/backup/`
- Копирую `backup-server` → `/opt/backup/`

**Итог на сервере:**

```
/opt/backup/
├── backup-server    ← бинарник (Linux)
├── config.toml      ← из bundle клиента
├── service.sh       ← для systemd
├── README.txt
└── tls/
    ├── server.crt
    └── server.key
```

Если сервер ругается на `tls/server.key` — выставь права:
```bash
chmod 600 tls/server.key
```

**Запускаю как сервис (чтобы после перезагрузки VPS поднялся сам):**

```bash
./service.sh
```

**Проверяю статус:**

```bash
systemctl status backup-server
```

**Шпаргалка systemctl:**

| Команда | Что делает |
|---------|------------|
| `sudo systemctl start backup-server` | Запустить |
| `sudo systemctl stop backup-server` | Остановить |
| `sudo systemctl restart backup-server` | Перезапустить (после правки config.toml) |
| `sudo systemctl enable backup-server` | Автозапуск при загрузке Linux |
| `sudo journalctl -u backup-server -f` | Логи в реальном времени |

### 1.5. Проверяю подключение с клиента

**Возвращаюсь на неттоп (Windows):**

Меню → **Подключения** → `bash02` → **Проверить подключение**

**Что происходит:**
1. Клиент проверяет TLS (свой CA, pinning)
2. При **первом успешном** подключении сервер запоминает `device_id` моего ПК с backup-client
3. Вижу: **«Подключение успешно»** ✅

[client-6.jpg]

**Важно про device_id**  
Сервер привязывается к **одному** клиенту (по `device_id`).  
Если скопируешь папку `client` на другой ПК, то сервер не разрешит подключение, пока на сервере не сбросишь привязку:

```bash
# На VPS в /opt/backup/config.toml
device_id = ""
```

Перезапустить сервис:
```bash
systemctl restart backup-server
```

Потом на **новом** ПК: **Проверить подключение** — и на сервер запишется новый `device_id`.

Если подключение не происходит, проверьте, открыт ли порт на сервере для внешних подключений.

Можно ограничить подключения к серверу, разрешить только IP клиента (если у вас выделенный IP, можно купить у провайдера за пару долларов).

```bash
# Для iptables
sudo iptables -A INPUT -p tcp --dport 8080 -s ТВОЙ_IP_КЛИЕНТА -j ACCEPT

# Для UFW
sudo ufw allow from ТВОЙ_IP_КЛИЕНТА to any port 8080 proto tcp
```

### 2.2. Настраиваю mysql_dump

**Заполняю форму:**

| Поле | Значение | Пример |
|------|----------|--------|
| **Имя задачи** | Любое | `mysite_db` |
| **Cron** | Расписание | `0 3 * * *` (каждый день в 3:00) |
| **Host** | Хост MySQL | `127.0.0.1` |
| **Port** | Порт MySQL | `3306` |
| **Database** | Имя базы | `wordpress` |
| **Username** | Пользователь MySQL | `wp_user` |
| **Password** | Пароль | `super_secret` |
| **mysqldump_path** | Путь к mysqldump | `/usr/bin/mysqldump` (обычно авто) |

> 💡 **Cron для теста**  
> Пока настраиваешь, поставь `*/5 * * * *` (каждые 5 минут) — быстро проверишь работу.  
> Когда всё работает — меняй на нормальное расписание, например в 8 утра `0 8 * * *`.

**Несколько задач?** Разнеси по минутам:
- Задача 1: `0 8 * * *`
- Задача 2: `5 8 * * *`
- Задача 3: `10 8 * * *`

Не все сразу в `:00` — чтобы не нагружать сервер.

## Часть 3. Production режим и шифрование (опционально)

### 3.1. Production режим (пароли БД на сервере, не на клиенте)

**Зачем:** Если украдут неттоп с `backup.db` — пароли от БД не утекут.

**Как включить:**

1. В backup-client → Подключения → bash02 → Secrets mode: Test (passwords on client) → Y
2. Проверить подключение — пароли задач удалятся с клиента, но останутся на сервере.

> **Как это работает**  
> В **Test** режиме: пароли БД хранятся в `backup.db` на клиенте (только для создания задач и теста).  
> В **Production** режиме: пароли только на сервере в `config.toml`. Клиент говорит «запусти задачу X», сервер сам подставляет пароли.

## Грабли, на которые я наступил

| Проблема | Причина | Решение |
|----------|---------|---------|
| **FileZilla портит бинарник** | Передаёт не в binary mode | WinSCP (Binary), FAR (SFTP), scp |
| **Exec format error** | Бинарник повреждён при копировании | Перезалить, проверить `file backup-server` |
| **Connection busy / device_id** | Другой ПК уже подключён | На сервере `device_id = ""` → restart |
| **mysqldump not found** | Неверный путь к mysqldump | `which mysqldump` → прописать в задаче |
| **Задача skip, encrypt** | Включил шифрование, но нет `encrypt_password` | Прописать в `config.toml` на сервере |
| **Файла нет на клиенте** | Планировщик не запущен | `backup-client.exe serve` или проверить Task Scheduler |
| **TLS handshake failed** | Сертификаты не совпадают | Пересоздать подключение (удалить `data\ca\bash02\`, добавить заново) |
